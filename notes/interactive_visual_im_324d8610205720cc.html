1.1 Why Spring?

Problem WITHOUT Spring (Plain Java)

In standard Java applications, classes construct their own dependencies directly, leading to tight coupling.

Java
// ❌ Tight Coupling — Every class creates its own dependencies
public class UserService {
    private UserRepository repo = new UserRepository(); // hardcoded!
}
public class UserController {
    private UserService service = new UserService();    // hardcoded!
}
warning Key Drawbacks of Plain Java
  • Tight Coupling: Classes depend on concrete implementations instead of interfaces.
  • Manual Object Management: new SomeClass() is scattered everywhere.
  • Difficult Testing: Inability to swap or mock implementations during unit tests.
  • Boilerplate Code: Repetitive configuration and instantiation setup.
  • No Lifecycle Management: Manual creation and destruction of resources.

Spring's Core Paradigm

Plain Java ProblemSpring Framework Solution
Tight CouplingIOC (Inversion of Control) → Loose Coupling via Interfaces
Manual ObjectsSpring Container manages all objects (Beans) automatically
Hard to TestDependency Injection (DI) makes swapping mock implementations seamless
Boilerplate CodeAuto-configuration + Annotations eliminate repetitive code
stars Interview Core Point
Strong answer: "Spring's IOC Container manages object creation and DI provides required dependencies, making code loosely coupled and highly testable."

Bean Lifecycle Stages

  2. 2

1.5 - 1.8 Dependency Resolution, Scopes & AutoConfig

Bean Conflict Resolution: @Qualifier vs @Primary

When multiple beans of the same interface type exist, Spring resolves conflicts as follows:

  • @Primary: Sets a default bean to inject when no explicit qualifier is named.
  • @Qualifier("beanName"): Specifies the explicit bean name to inject (case-sensitive).
  • Rule: @Qualifier always beats @Primary (Specific > Default).

Bean Scopes

ScopeInstances CreatedState Rule@PreDestroy Called?
Singleton (Default)1 shared instance per containerMust be STATELESS!✅ Yes
PrototypeNew instance per request/injectionCan carry state❌ No (You manage cleanup)
Request / SessionPer HTTP Request / User SessionWeb scoped state✅ Yes

AutoConfiguration Mechanics

Spring Boot triggers auto-configuration via @EnableAutoConfiguration, reading AutoConfiguration.imports and validating @ConditionalOnClass and @ConditionalOnMissingBean.

key Golden Rule of AutoConfiguration
Your custom bean ALWAYS wins. Because Spring AutoConfig uses @ConditionalOnMissingBean, if you define your own custom bean, Spring Boot skips its default auto-configured bean!

2.1 Spring MVC Architecture & DispatcherServlet

DispatcherServlet acts as the central Front Controller for every incoming HTTP request in Spring MVC.

Complete Request Processing Flow

  1. 1
    Client Request: HTTP Request arrives at embedded Tomcat (e.g., GET /api/users/1).
  2. 2
    DispatcherServlet: Intercepts request and consults HandlerMapping.
  3. 3
    HandlerMapping: Resolves URL mapping to target `@RestController` method.
  4. 4
    Controller Execution: Controller executes service logic and returns Java object/DTO.
  5. 5
    HttpMessageConverter (Jackson): Serializes Java DTO into JSON response payload.

2.4 Global Exception Handling (@RestControllerAdvice)

Java
@RestControllerAdvice
public class GlobalExceptionHandler {

    // 1. Handle Custom Business Exceptions
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(ResourceNotFoundException ex, HttpServletRequest req) {
        ErrorResponse error = ErrorResponse.builder()
                .status(404).message(ex.getMessage()).path(req.getRequestURI()).timestamp(LocalDateTime.now()).build();
        return ResponseEntity.status(404).body(error);
    }

    // 2. Handle DTO Validation Failures (@Valid)
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException ex) {
        Map<String, String> errors = new HashMap<>();
        ex.getBindingResult().getFieldErrors().forEach(e -> errors.put(e.getField(), e.getDefaultMessage()));
        return ResponseEntity.badRequest().body(ErrorResponse.builder().status(400).fieldErrors(errors).build());
    }
}

3.3 Entity Relationships & Owner Concept

link Relationship Owner Rule
The Owner side contains the Foreign Key (FK) column in the database (e.g., `@ManyToOne`). The Non-Owner side uses mappedBy = "fieldName" referencing the field in the owner class. mappedBy is ONLY placed on the non-owner side!
Java Entity Relationship
// OWNER SIDE (Contains FK Column)
@Entity
public class Post {
    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;
}

// NON-OWNER SIDE (Refers to owner field)
@Entity
public class User {
    @OneToMany(mappedBy = "user", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
    private List<Post> posts = new ArrayList<>();
}

3.4 EAGER vs LAZY Loading & N+1 Problem

Default Fetch Types (Memorize!)

AnnotationDefault Fetch TypeRecommended Action
@OneToManyLAZY ✅Keep Default
@ManyToManyLAZY ✅Keep Default
@ManyToOneEAGER ⚠️Override to LAZY!
@OneToOneEAGER ⚠️Override to LAZY!

Solving the N+1 Problem with JOIN FETCH

Executing findAll() with LAZY associations causes 1 initial query + N additional queries per child item. Fix it using JOIN FETCH:

Java Repository JPQL
// Solves N+1 in a single query!
@Query("SELECT p FROM Post p JOIN FETCH p.user")
List<Post> findAllWithUser();

3.5 - 3.6 @Transactional & Pagination

warning Critical Proxy Bug: Self Invocation
Calling a @Transactional method from within the same class (e.g., this.createUser()) bypasses the Spring AOP Proxy, causing transaction management to fail silently! Move transactional methods to a separate Spring Service Bean.

6.1 JUnit 5 Fundamentals & AAA Pattern

The AAA Pattern

Java Test Structure
@Test
void add_Success() {
    // 1. ARRANGE — Setup test fixtures
    int a = 5, b = 10;

    // 2. ACT — Execute method under test
    int result = calculator.add(a, b);

    assertEquals(15, result);
}

6.2 - 6.3 Mockito Framework & Complete Production Suite

@Mock vs @InjectMocks

AnnotationRoleAnalogy
@MockCreates a fake dummy instance of a dependency (Repository/API)Stunt Double / Fake Object
@InjectMocksCreates target class under test & injects all `@Mock` objects into itTarget Service Under Test

Complete Mockito Test Suite Example

Java (JUnit 5 + Mockito)
@ExtendWith(MockitoExtension.class)
class StudentServiceTest {

    @Mock private StudentRepository studentRepository;
    @InjectMocks private StudentService studentService;

    @Test
    @DisplayName("Should throw ResourceNotFoundException when student ID not found")
    void getStudentById_NotFound() {
        // 1. ARRANGE
        when(studentRepository.findByIdWithCourses(99L)).thenReturn(Optional.empty());

        // 2. ACT & ASSERT
        ResourceNotFoundException ex = assertThrows(
                ResourceNotFoundException.class,
                () -> studentService.getStudentById(99L)
        );

        assertEquals("Student not found with id: 99", ex.getMessage());
        verify(studentRepository, times(1)).findByIdWithCourses(99L);
    }
}
